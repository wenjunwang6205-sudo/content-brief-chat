# 企业内部智能助手 — 能力映射说明

> 本文档不出现任何具体企业名称。  
> 演示项目：**ContentBrief Chat**（快消内容团队场景）  
> 对标能力：**企业级对话助手**（知识问答 · 任务执行 · 增长闭环）

---

| 企业助手能力 | ContentBrief 现状 | 说明 |
|--------------|-------------------|---------|

## 2. 核心链路（与企业智能助手能力对齐）

```
用户输入
  → 意图识别（问知识 / 办任务 / 修订 / 合规 / 转人工 / 闲聊）
  → 路由（RAG / Brief Agent / 拒答 / 固定话术）
  → 任务状态机（补槽 → 生成 → 修订 → 确认 → 完成）
  → 观测（任务成功率、耗时、修订率）
```

## 3. 从 Demo 到工业级可用：RAG 工程化

构建企业级 AI 助手，核心挑战在于从「技术 Demo」向「工业级可用」演进。历史资料治理、知识持续更新、千人规模下的检索性能，分别对应 RAG（检索增强生成）系统的三个支柱：**数据工程（Data Engineering）**、**数据生命周期管理（Data Lifecycle）**、**架构性能优化（Infrastructure Optimization）**。

> **与本 Demo 的关系：** ContentBrief Chat 在 V0 使用 `knowledge/` 扁平语料 + 元数据 + 引用溯源，验证「问答 + 任务」产品范式；下列方案描述的是企业级知识中台（大图 M1）的演进方向，而非当前仓库已全部实现。

### 3.1 历史资料的「清洗与结构化」：从混乱到清晰

庞大的企业历史资料（PDF、Word、Wiki、图片、表格）直接切片入库会导致严重的「垃圾进、垃圾出（GIGO）」。必须通过体系化的数据治理管线进行处理。

**1. 自动化解析与结构化（Parsing）**

- **多模态解析：** 放弃传统纯文本提取，使用基于布局感知（Layout-aware）的解析（如 LayoutLM、Docling 或大模型视觉解析），将 PDF/文档转化为带语义标签的 Markdown 或 JSON。
- **表格与图表：** 表格不宜直接切片。需转为 Markdown，或由大模型总结为文本描述（Summary），以「文本描述 + 原始表格」为一组入库。

**2. 语义切片（Semantic Chunking）**

- 避免固定字符长度（如每 500 字）的粗暴切分。
- 采用**按文档结构切片**（H1 / H2 / H3 层级）或**语义动态切片**（监测相邻句向量相似度，突变处断句）。

**3. 多粒度索引（Multi-vector Indexing）**

- **父子分块（Parent-Child）：** 小子块用于精准向量匹配，大父块为 LLM 提供完整上下文。
- **摘要索引：** 对长篇资料生成摘要，先匹配摘要，再定位具体章节。

**4. 知识图谱（GraphRAG，可选）**

- 纯向量检索难以回答「A 项目谁负责、此人前序项目有哪些」等跨文档关联。
- 用 LLM 抽取实体（部门、项目、人员、产品）与关系，构建知识图谱，**向量检索 + 图检索** 结合，缓解资料碎片化。

### 3.2 知识库的「持续更新与动态维护」

静态知识库往往数月内失效，需建立自动化的增删改查与生命周期管理。

**1. 触发型同步（CDC & Webhooks）**

- 避免仅依赖全量定时刷新。
- 通过 Confluence、SharePoint、飞书、钉钉等 **Webhooks**，或数据库 **CDC（变更数据捕获）**，在文档创建/修改/删除时实时或准实时触发管线，**局部更新**向量库。

**2. 元数据治理（Metadata Tagging）**

每个 Chunk 建议强制标签：

| 字段 | 用途 |
|------|------|
| Timestamp | 创建/更新时间 |
| Version | 版本号 |
| Owner | 业务负责人/部门 |
| Status | 有效 / 废弃 / 暂不公开 |

**3. 冲突与时效性**

- **时间衰减权重：** 检索时对较新文档加分，废弃文档降权。
- **显式覆盖：** 新文档入库（如《2026 报销流程》）时，通过元数据将旧版标为 `Deprecated`，默认检索范围剔除。

### 3.3 千人规模下的「快速与精准查询」

海量资料与高并发下，全库向量搜索易导致延迟高、准确率下降，需多级检索与架构分流。

**1. 混合检索 + 元数据前置过滤**

- **Pre-filtering：** 按用户身份与上下文（如 HR 提问）先用元数据缩小检索范围（可至原来的 1/100～1/1000）。
- **Hybrid Search：** **BM25（关键词）** + **Dense Retrieval（向量）**，兼顾专有名词与语义。

**2. 两阶段检索：粗排 + 重排（Reranking）**

| 阶段 | 手段 | 目标 |
|------|------|------|
| 粗排 | HNSW、IVF-PQ 等索引 | 毫秒级从百万级召回 Top-50 |
| 精排 | Cross-Encoder / Reranker | 筛出 Top-5～10 进 LLM 上下文 |

**3. 语义缓存（Semantic Cache）**

- 行政、IT、高频政策等问题重复度高。
- 使用 GPTCache 等：新问题与历史问句语义相似度 > 阈值（如 0.95）时直接返回缓存，耗时毫秒级，绕过检索与生成。

**4. 向量库分布式架构**

- 采用支持读写分离、水平扩展的向量库（如 Qdrant、Milvus）。
- **只读副本**分担并发，目标将检索 P95 稳定在约 **50ms** 量级（视集群与数据量而定）。

### 3.4 与本项目 Demo 的对照（V0 → V1）

| 工程能力 | ContentBrief V0 | 企业级目标 |
|----------|-----------------|------------|
| 语料形态 | 结构化 Markdown + `doc_id` | 多模态解析 + 语义切片 |
| 更新方式 | 随仓库发布 | CDC / Webhook 增量 |
| 检索 | 单库 RAG + 引用 | 混合检索 + 权限过滤 + Rerank |
| 规模 | 演示级语料 | 分布式向量库 + 语义缓存 |

## 4. 北极星指标（演示期定义）

| 指标 | 定义 |
|------|------|
| 任务成功率 | 用户点击「标记任务完成」/ Brief 任务开始数 |
| 一次完成率 | 无多次 `task_started` 即完成 |
| 引用覆盖率 | 有引用的 QA 回答占比 |
| 修订率 | 使用 brief_refine 的任务占比 |

详见 [产品PRD](./产品PRD.md) 与 [测试说明](./测试说明.md)。

## 5. 演示路径（约 3 分钟）

1. 打开 Pages 链接 → 点「品牌调性」芯片 → 看流式回答与引用  
2. 输入或点芯片生成 618 Brief → **「把人群改成 Z 世代」** 看修订摘要  
3. 导出 → **标记任务完成**  
4. 刷新页面 → 会话仍在  
5. （可选）`?debug=1` 看任务成功率

## 1. 什么是「内容团队提效系统」

**不是**某一个聊天窗口，而是支撑品牌**内容生产与投放准备**的一组产品能力组合，目标是：

- 缩短从「对齐口径」到「可执行 Brief/脚本」的周期  
- 降低新人与外包的**合规与事实错误**  
- 让知识（品牌、产品、渠道、法规）**可检索、可引用、可迭代**  

典型使用部门：品牌部、内容策划、社媒运营、部分投放协同同学。

本分析以**饮料品牌内容团队**为样本（高糖/无糖/电解质等 SKU 多、季节营销密、渠道规范差异大）。

## 2. 业务现状与痛点（As-Is）

### 2.1 内容团队主价值链

```
市场/品牌策略 → 活动/选题策划 → Brief&脚本 → 多渠道改稿 → 合规审核 → 发布 → 复盘
                     ↑_________________ 本系统重点覆盖 _________________↑
```

### 2.2 角色与核心诉求

| 角色 | 日常产出 | 核心诉求 | 当前主要工具 |
|------|----------|----------|----------------|
| 内容策划 | 活动 Brief、达人 Brief、脚本大纲 | 快、格式统一、少返工 | 飞书文档、微信群、历史 Brief |
| 品牌经理 | 调性把关、卖点口径 | 口径一致、可追责 | 品牌手册 PDF、口头同步 |
| 社媒运营 | 按渠道改标题/结构 | 懂平台规则、不踩线 | 各平台运营文档、同事经验 |
| 团队负责人 | 质量与效率 | 可度量、可复盘、旺季扛量 | Excel、项目群 |

### 2.3 痛点归纳（需求来源）

| ID | 痛点 | 表现 | 影响 | 需求方向 |
|----|------|------|------|----------|
| P1 | 知识分散 | 品牌/渠道/合规散落在多份文档 | 检索慢、新人问人 | **统一知识服务** |
| P2 | Brief 产能瓶颈 | 大促前堆需求，模板不统一 | 延期、质量波动 | **结构化生成 + 模板** |
| P3 | 事实与合规风险 | 价格/功效/绝对化用语 | 法务返工、下架风险 | **拒答/提示 + 引用** |
| P4 | 协作断层 | Brief 与改稿、审核系统割裂 | 重复劳动 | 后续：工作流衔接（V1+） |
| P5 | 质量不可运营 | 好坏凭感觉 | 难迭代 | **评测 rubric + badcase** |

## 3. 需求范围界定

### 3.1 In Scope（系统规划内）

| 能力域 | 说明 | 优先级 |
|--------|------|--------|
| 品牌/产品/渠道/合规知识服务 | 问答、检索、引用 | P0 |
| 活动 Content Brief 生产 | 补槽、生成、修订、确认导出 | P0 |
| 内容质量评测体系 | 维度、badcase、回归 | P0 |
| 对话式统一入口 | 自然语言 + 意图路由 | P0 |
| 渠道文案适配、素材 DAM、投放数据 | 明确后置 | P2+ |

### 3.2 Out of Scope（本期不承诺）

- 达人撮合、投放执行、电商交易  
- 多品牌多租户、SSO、完整权限审计  
- 替代创意决策（口味、代言人等战略选择）

---

## 4. 机会 prioritization（为什么先做什么）

| 机会 | 价值 | 可行性 | 决策 |
|------|------|--------|------|
| 统一知识问答 + 引用 | 日课高频，立刻减负 | RAG + 知识库可演示 | **P0** |
| Brief 结构化生成 | 旺季痛点，易验收 | 模板 + LLM 成熟 | **P0** |
| 全渠道自动发稿 | 价值高 | 对接多、风险大 | 后置 |
| 舆情/竞品洞察 | 有价值 | 另一产品链路 | 不在本系统 V0 |

**结论：** V0 切口 = **「对话入口：查得到 + Brief 办得完」**，对应可运行 Demo **ContentBrief Chat**。

## 5. 目标用户与关键场景（用户需求层）

### 5.1 用户需求陈述（User Needs）

| UN-ID | 需求（用户语言） | 对应痛点 |
|-------|------------------|----------|
| UN-01 | 我想秒查品牌调性和禁用表述 | P1、P3 |
| UN-02 | 我想按模板快速出活动 Brief 初稿 | P2 |
| UN-03 | 我想知道答案出自哪份官方文档 | P1、P3 |
| UN-04 | 信息不够时系统应追问而不是瞎编 | P3 |
| UN-05 | 导出前我要确认并对修改负责 | P3、P5 |
| UN-06 | 改 Brief 时只改相关段落 | P2 |

### 5.2 典型场景（饮料快消）

1. **大促前 2 周**：策划并行多个 618/双11 活动，需多份 Brief。  
2. **新品上市**：对齐 SKU 卖点与合规表述，渠道话术不一。  
3. **新人 onboarding**：频繁问小红书标题、直播话术禁忌。  
4. **忙季合规**：外包文案需统一扫描绝对化用语。

## 6. 成功指标（系统级，非仅 Demo）

| 指标 | 定义 | V0 演示目标 |
|------|------|-------------|
| Brief 首稿耗时 | 从需求输入到可导出 Markdown | 显著短于纯人工（定性） |
| 引用覆盖率 | 问答类回答含有效引用占比 | 命中知识库时 100% |
| 合规拦截率 | 价格/绝对化等触发 guard 占比 | badcase 回归通过 |
| 任务完成率 | 用户确认完成 Brief 任务 | 演示路径可走通 |

---

## 7. 约束与假设

- 知识库为**虚构品牌「澄澈饮力」**，不代表真实客户数据。  
- LLM 通过 API 调用（如 DeepSeek/OpenAI 兼容），Key 仅服务端配置。  
- 人机协同：**生成辅助，人确认交付**。

## 1. 背景与目标

### 1.1 背景

饮料品牌内容团队日常需完成：品牌口径统一的知识查询、大促/新品/季节活动的 **Content Brief** 撰写、多渠道（小红书、抖音、直播等）内容适配与合规审核。当前痛点包括：

- Brief 撰写依赖资深同学经验，**周期长、格式不统一**
- 品牌调性、渠道规范、广告法约束分散在文档与口口相传中，**检索成本高**
- 新人上手慢，**合规与事实错误**在忙季频发

### 1.2 产品定位

**ContentBrief Chat** 是面向内容/品牌团队的**企业级对话助手**（演示项目），作为员工高频工作入口之一，完成：

1. **知识问答与信息检索**（品牌、产品、渠道、合规）
2. **活动 Content Brief 任务闭环**（多轮补全 → 结构化产出 → 人工确认 → 导出）

设计范式适用于任意企业内部智能助手场景；本仓库以**饮料快消**作为验证场景，**不涉及任何真实企业名称或内部数据**。

### 1.3 目标（V0 演示版）

| 目标 | 说明 | 目标值（演示） |
|------|------|----------------|
| 任务完成 | 用户可在一次会话内获得可交付 Brief 草案 | 主流程可走通 |
| 效率 | 相对纯人工撰写首稿 | 耗时显著缩短（演示定性） |
| 质量 | 品牌一致、合规、可引用 | 评测维度均分 ≥ 4/5（见 测试说明.md） |
| 可控 | 无依据不编造、关键结论可溯源 | 100% 带引用或明确追问 |

### 1.4 非目标（V0 不做）

- 完整内容资产管理（DAM）、投放、达人、电商交易
- 多租户权限、SSO、审计日志（生产级）
- 自动化全渠道发布
- 真实企业 ERP/产品主数据对接

## 2. 用户与场景

### 2.1 目标用户

| 角色 | 诉求 |
|------|------|
| 内容策划 | 快速产出活动 Brief，对齐品牌与渠道 |
| 品牌经理 | 查调性、禁用词、竞品话术边界 |
| 社媒运营 | 按渠道规范改稿、避免合规雷区 |
| 团队负责人 | 统一模板、可复盘、可评测的质量标准 |

### 2.2 典型场景（饮料）

1. **知识问答**：「夏季主推无糖茶的品牌主张是什么？」「小红书标题字数上限？」
2. **活动 Brief**：「为 618 电解质饮料做抖音种草 Brief，人群为运动青年」
3. **合规辅助**：Brief 中出现敏感表述时提示修改建议
4. **追问补全**：用户未提供预算/渠道/人群时，助手主动追问而非胡编

### 2.3 用户故事

| ID | 作为… | 我希望… | 以便… |
|----|--------|---------|--------|
| US-01 | 内容策划 | 用自然语言提问品牌与渠道规范 | 不用翻多个文档 |
| US-02 | 内容策划 | 根据活动目标生成结构化 Brief | 缩短首稿时间 |
| US-03 | 品牌经理 | 看到建议内容引用的知识来源 | 确认口径可追溯 |
| US-04 | 内容策划 | 在导出前修改并确认 Brief | 人对最终交付负责 |
| US-05 | 运营负责人 | 对生成内容有明确质量维度 | 持续迭代 prompt 与知识库 |

## 4. 功能需求

### 4.1 功能列表

| 模块 | 功能 | 优先级 | 说明 |
|------|------|--------|------|
| 对话 | 多轮会话 | P0 | 保留上下文（会话级） |
| 意图 | 知识问答 | P0 | 基于知识库回答，带引用；**单入口自动识别** |
| 意图 | Brief 任务 | P0 | 结构化产出 + 确认导出 |
| RAG | 知识检索 | P0 | 检索 top-k 片段注入 prompt |
| 体验 | 引用溯源 | P0 | 展示 doc_id / 标题 / 摘录 |
| 体验 | 追问引导 | P0 | 缺必填槽位时追问 |
| 体验 | 失败兜底 | P0 | 无法回答时说明原因，不编造 |
| 体验 | 人机确认 | P0 | 用户确认后再导出 Markdown |
| 合规 | 敏感词提示 | P1 | 输出后扫描禁用/绝对化用语 |
| 运维 | 限流 | P0 | 公网 Demo 按 IP 限流（无 Token） |
| 部署 | Vercel API | P0 | 代理 LLM，Key 仅环境变量 |

### 4.2 知识库范围（单一 RAG 语料库）

路径规划（开发阶段创建，本文档仅定义结构）：

```
knowledge/
├── brand/          # 品牌调性、视觉话术原则
├── product/        # 饮料 SKU、卖点、成分事实（虚构）
├── channel/        # 小红书/抖音/直播规范
├── compliance/     # 广告法、禁用词、敏感表述
└── cases/          # 历史活动 Brief 样例（优质）
```

**不区分多企业库**：一套饮料演示知识库；迁移时整体替换语料即可。

### 4.3 Brief 输出结构（P0 固定模板）

生成内容须包含以下章节（Markdown）：

1. 活动背景与目标  
2. 目标人群与洞察  
3. 核心信息与卖点（须引用 product/ 或 brand/）  
4. 渠道与内容形式建议  
5. 调性关键词与参考句式  
6. 合规注意事项  
7. 待确认项（若有）

### 4.4 对话模式说明

#### 模式 A：知识问答

- **输入**：自然语言问题  
- **处理**：RAG 检索 → LLM 生成 → 附 `citations[]`  
- **输出**：回答正文 + 可点击引用卡片  
- **异常**：检索置信度低 → 提示「知识库中未找到，请补充或联系管理员」

#### 模式 B：Brief 任务

- **输入**：活动描述（至少：活动名/目标；可选：人群、渠道、时间）  
- **处理**：槽位检查 → 缺则追问 → 检索 → 按模板生成 → 展示预览  
- **输出**：结构化 Brief + 引用  
- **确认**：用户点击「确认并导出」后下载/复制 Markdown  
- **异常**：用户取消 → 保留草稿在会话内

### 4.5 必填槽位（Brief 模式）

| 槽位 | 必填 | 缺失时行为 |
|------|------|------------|
| 活动/ campaign 名称 | 是 | 追问 |
| 主推产品（饮料 SKU） | 是 | 追问 |
| 目标（曝光/种草/转化） | 是 | 追问 |
| 目标人群 | 否 | 可用默认「待补充」标注 |
| 主渠道 | 否 | 默认多渠道建议 |

## 5. 体验与交互（企业助手范式）

| 原则 | 实现要求 |
|------|----------|
| 从问答到任务 | Brief 模式必须产出可交付文档，而非仅聊天 |
| 引用溯源 | 每条核心结论尽量对应 ≥1 条 citation |
| 追问引导 | 缺槽位时单次最多追问 2 个问题，避免审问感 |
| 失败兜底 | 无依据不输出虚假促销、价格、功效 |
| 人机协作 | 导出前必须经用户确认（明确按钮） |
| 结果呈现 | Brief 分区展示，引用侧边或折叠面板 |

*线框图与视觉规范在 Demo 开发阶段补充至 `/demo`。*

## 6. 技术方案（计划）

### 6.1 架构

```
[GitHub Pages — 静态前端]
        │ HTTPS POST /api/chat
        ▼
[Vercel Serverless — api/chat]
  · 环境变量：LLM_API_KEY、LLM_BASE_URL（可选）
  · RAG：读取 knowledge/（构建时打包或运行时读取）
  · 限流：按 IP（如 10 req/min）
        ▼
[大模型 API — OpenAI 兼容]
```

### 6.2 安全与公网策略

- **不提供 DEMO_TOKEN**（按项目决策）：依赖 IP 限流 + token 上限 + 供应商侧预算告警  
- API Key **禁止**进入前端仓库与 GitHub Pages 构建产物  
- README 注明：公开演示，请勿压测  

### 6.3 技术栈（计划）

| 层级 | 选型 |
|------|------|
| 前端 | Vite + React + TypeScript + Tailwind |
| 后端 | Vercel Functions（Node） |
| 模型 | 由维护者配置（OpenAI 兼容接口） |
| 检索 V0 | 关键词 + 简单评分（可升级 embedding） |

## 7. Prompt 与上下文（概要）

### 7.1 System Prompt 要点

- 角色：饮料品牌内容团队助手  
- 约束：仅依据提供的知识库片段回答；无依据则追问或拒答  
- 输出：问答模式简洁；Brief 模式严格 JSON 或 Markdown 模板  
- 合规：禁止使用绝对化用语，命中 compliance/ 片段时提醒  

### 7.2 上下文组装

```
system + rules
+ retrieved_chunks（带 doc_id，供 citations）
+ conversation_history（最近 N 轮）
+ user_message
```

### 7.3 AI Builder 记录（开发时补充）

在 `docs/` 或 README 附录记录：Dify/Cursor 试 prompt 的版本对比、选用理由（开发阶段填写）。

## 9. 验收标准

### 9.1 功能验收

- [ ] 知识问答：3 个标准问题回答正确且带引用

- [ ] 通过 [测试说明](./测试说明.md) 中 P0 用例

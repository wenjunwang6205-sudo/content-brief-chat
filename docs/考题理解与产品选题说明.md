## 1. 对题目要求的理解

题目通常包含两层考察，需要**分开交付、又前后呼应**：

| 层次 | 题目要求 | 考察点 | 本仓库对应物 |
|------|----------|--------|----------------|
| **第一层** | 基于内容团队提效系统，输出**需求分析**和**产品大图** | 系统思维：边界、模块、优先级、与业务链路关系 | [PRD.md](./PRD.md) §1–3、[enterprise-capability-mapping.md](./enterprise-capability-mapping.md) |
| **第二层** | **选一个切入点**，做**详细需求设计** | PRD 功底：用户故事、功能列表、状态机、验收标准、异常与合规 | [PRD.md](./PRD.md) §4–10、[V2-PRD.md](./V2-PRD.md)、[testing.md](./testing.md) |
| **隐含** | **AI 试用情况** | 不是「会不会调 API」，而是：能力边界、RAG、评测回归、可演示闭环 | 在线 Demo + `knowledge/` + `eval/` + `npm run eval` |

**行业约束（快消）** 的含义：

- 用户是**品牌/内容/社媒**角色，不是通用 C 端消费者。
- 知识库内容是**品牌调性、SKU、渠道规范、广告法**，不是百科问答。
- 典型交付物是 **Content Brief / 活动方案片段**，不是长篇投标全案（那是另一条产品线）。
- 合规与**事实可追溯**权重大于「写得好看」。

## 2. 产品大图：内容团队提效系统（我们在答什么）

饮料（及更广的快消）内容团队的一条主链路可以概括为：

```
洞察与口径 → 活动策划 → Brief/脚本 → 多渠道适配 → 合规 → 发布与复盘
```

其中 **信息检索成本高**、**Brief 首稿慢且格式不一**、**合规踩线** 是三个高频、可产品化的痛点。

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ 品牌/产品   │   │ 选题/活动   │   │ Brief&脚本  │   │ 合规审核    │
│ 知识库      │──▶│ 策划辅助    │──▶│ 生成 ★切口  │──▶│ 提示        │
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
        │                                    │
        └────────────────┬───────────────────┘
                         ▼
              ┌─────────────────────┐
              │ ContentBrief Chat   │  ← 演示切口：统一对话入口
              │ 知识问答 + Brief 任务 │
              └─────────────────────┘
```

**为什么不是一上来做「全系统」？**

- 考题第二层要的是**切口上的 PRD 深度**，不是一张画满箭头的 PPT。
- 切口选 **「对话入口：查得到 + 办得完」**，能同时覆盖：
  - **高频日课**（查规范、查调性）→ 证明 RAG 与引用；
  - **周期性重任务**（大促 Brief）→ 证明任务闭环、多轮补槽、人工确认。

后续可扩展（口述即可，不必 V0 全做）：渠道改写、素材 DAM、投放数据回流、A/B 文案等。

## 3. 切入点选择：为什么是「企业对话助手」而不是别的

| 可选切口 | 优点 | 为何不选为 V0 主切口 |
|----------|------|----------------------|
| 纯表单生成 Brief | 实现简单 | 无法体现**检索、多轮澄清、引用溯源**；不像「助手」 |
| 纯知识库搜索 | 开发量小 | 只解决「查」，不解决「交付物」；难以体现任务成功率 |
| 合规扫描工具 | 差异化 | 偏单点工具，难覆盖内容策划主流程 |
| **对话助手：问答 + Brief 任务** | 贴近「企业智能助手」范式；可演示完整链路 | 实现复杂度适中，**最适合同时交 PRD + AI 试用** |

**结论：** 切口 = **ContentBrief Chat** —— 内容团队的一个**统一工作入口**，承担两类意图：

1. **knowledge_qa**：问品牌 / 渠道 / 合规，**带引用**。  
2. **brief_create / brief_refine**：办活动 Brief，**多轮补槽 → 生成 → 修订 → 确认导出 → 任务完成**。

这与快消内容团队的「先对齐口径，再出 Brief，再改稿」节奏一致。

## 4. 为什么要做「当前这种内容形态」

### 4.1 为什么是「饮料快消」场景

- 题目明确快消；**饮料**子类知识结构化程度高（SKU、成分声称、季节营销），适合 RAG + 模板化 Brief。
- 虚构品牌 **澄澈饮力** 可规避真实客户保密，又保留行业话术（电解质、无糖茶、618、小红书种草等）。

### 4.2 为什么是「结构化 Brief」而不是自由长文

| 维度 | 说明 |
|------|------|
| 可验收 | 固定 7 章节能写进 PRD 与 `testing.md`，便于评测与 badcase |
| 可交付 | 导出 Markdown，模拟「确认后交给设计/投放」 |
| 可控 | 缺槽追问，避免模型一次胡编完整方案 |
| 行业习惯 | 内容团队普遍有 Brief 模板，不是从零写散文 |

### 4.3 为什么强调引用、合规、评测

快消内容 **广告法 / 绝对化用语 / 价格事实** 风险高。产品设计选择：

- **无依据不编造**（价格、折扣拒答或进「待确认项」）；
- **引用溯源**（脚注 + 知识库原文）；
- **8 维 rubric + badcase 回归**（`testing.md`、`eval/cases/`）—— 对应「AI 不是 demo 一下，而是可运营迭代」。

### 4.4 为什么用对话，而不是两个独立产品

内容同学的一天是**交织的**：先查「小红书标题规范」，再写「618 Brief」，再改「人群改成 Z 世代」。  
**统一会话**更符合真实工作流，也符合企业助手「一个入口多种意图」的考察方向。

## 5. 关于「知识问答 / Brief」两个模式：要不要两个入口？

### 5.1 结论（产品判断）

**对考官演示：一个入口就够。**  
用户只面对**一个输入框**，用自然语言或建议芯片表达意图；系统通过 **意图识别 + 路由** 分流即可。

顶部「知识问答 / Brief 任务」下拉属于 **V1 简化交互**，在已有 V2 意图路由后：

| 保留双模式切换 | 单一入口 + 意图路由 |
|----------------|---------------------|
| 降低首次理解成本（演示时好讲「现在切到 Brief」） | 更贴近真实企业助手（无需用户先选模式） |
| 与自动识别可能「打架」（用户切了 Brief 却在问知识） | 建议芯片仍可引导场景，但不强制模式 |
| 略显「产品未完成自动路由」 | 更能体现 AI PM 对 **路由与 FSM** 的设计 |

**推荐演进：**

- **对外叙事**：统一为「内容团队助手」，一种入口。  
- **对内实现**：保留 `mode` 仅作**弱提示 / 兜底**（与 `detectIntent` 一致时以意图为准）。  
- **UI**：可去掉 Header 下拉，改为空状态芯片 + 输入框占位文案（如「问规范，或描述活动需求…」）。

若时间紧，**保留切换也不扣分**，面试时主动说：「V1 为降低理解成本；V2 已支持自动识别，下一步会收拢为单入口。」

### 5.2 能力本身仍需两类，不是合并成一个功能

「一个入口」≠「只做问答」或「只做 Brief」。  
考察要点是：**同一助手既能查（RAG），又能办（任务闭环）**—— 只是不必让用户手动选模式。
